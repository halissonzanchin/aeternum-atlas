## 1. INVENTÁRIO DE DADOS LEGADOS NO NAVEGADOR (`localStorage`)

Historicamente, parte substancial do progresso de dissecção e repetição espaçada dos estudantes residia apenas no armazenamento local do navegador do dispositivo (`localStorage`), ficando vulnerável à perda de dados em limpezas de cache ou na troca de computador.

| Chave Legada | Tipo de Dado | Conteúdo / Significado | Destino Canônico no Supabase |
|---|---|---|---|
| `completedModels` | Array de Strings | IDs de peças 3D marcadas como 100% concluídas. | `public.user_model_progress` (`completion_percent = 100`) |
| `favorites` | Array de Strings | IDs de peças 3D favoritadas pelo estudante. | `public.user_model_progress` (`is_favorite = true`) |
| `studyProgress` | Objeto JSON | Duração acumulada por modelo e último acesso. | `public.user_model_progress` (`time_spent_seconds`, `last_accessed_at`) |
| `savedDecks` | Array de Objetos | Baralhos e flashcards criados localmente. | `public.user_flashcards` / `public.user_flashcard_reviews` |
| `sm2Data` | Objeto JSON | Intervalos, fatores de facilidade e repetições SM-2. | `public.user_flashcard_reviews` (`interval_days`, `ease_factor`) |

## 2. ESTRATÉGIA DE TRANSIÇÃO SUAVE E IDEMPOTENTE

A migração foi arquitetada para ser **completamente não-destrutiva** e invisível ao estudante, seguindo o padrão *Dual-Read / Dual-Write / Prioritized Cloud*:

```
          [ Inicialização da Sessão do Estudante ]
                             │
                             ▼
              Existe sessão autenticada ativa?
                   ├── NÃO ──► Usar Cache Local do Navegador (Modo Offline)
                   │
                   └── SIM ──► Consultar Supabase (RPC get_student_academic_summary)
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
       Banco possui dados?                     Banco vazio / incompleto?
                 │                                       │
                 ▼                                       ▼
    Adotar Nuvem como Verdade                Verificar localStorage local
    Atualizar Cache Local                    Executar Sincronização Idempotente
                                             (legacyTelemetrySyncService.syncLegacyProgress)
                                                         │
                                                         ▼
                                             Persistir no Supabase de forma Atômica
```

### Regras de Idempotência
1. **Chaves Únicas Compostas:** Na tabela `public.user_model_progress`, o par `(user_id, model_id)` é estritamente único. Operações de migração utilizam `ON CONFLICT (user_id, model_id) DO UPDATE`.
2. **Preservação do Maior Progresso:** Se o banco já possuir 80% de conclusão em um modelo e o navegador local apresentar 100%, o valor é promovido para 100%. Se o navegador tiver 40% e o banco 80%, o valor de 80% é mantido intacto.
3. **Não-Duplicação de Intervalos:** Sessões legadas locais são confrontadas com as sessões persistidas em `public.user_active_sessions`. Sessões já gravadas na nuvem são ignoradas.

## 3. SINCRONIZAÇÃO MULTI-DISPOSITIVO E RESILIÊNCIA OFFLINE

Um estudante frequentemente acessa a Aeternum Atlas no laboratório da faculdade e no seu notebook pessoal em casa:
1. **Proteção contra Sobrescrita Tardia:** Eventos de dissecção transmitem carimbos de data/hora (`timestamp` UTC ISO 8601). Em caso de conflito, a ordenação cronológica estrita é aplicada.
2. **Buffer Local para Operação Offline:** Se o estudante estiver estudando em local com conexão oscilante, os eventos são enfileirados no `localStorage` sob a chave `_aeternum_pending_telemetry_v2`. Assim que a conectividade for restabelecida, o serviço descarrega os eventos em lote na RPC canônica.
3. **Respeito ao FIRST SESSION WINS:** Dispositivos secundários que tentem sincronizar telemetria sem uma sessão prioritária autorizada são colocados em espera pelo `SessionGuardService`, impedindo contaminação cruzada de estados.

## 4. CONFORMIDADE COM PRIVACIDADE E MULTI-TENANCY (LGPD / GDPR)

A telemetria de estudo do estudante constitui dado pessoal e acadêmico protegido por lei:
1. **Row Level Security (RLS) Estrito:**
   - Estudantes possuem permissão estritamente restrita aos seus próprios registros (`auth.uid() = user_id`). Nenhuma query direta do frontend pode consultar métricas de outros estudantes.
   - Professores e Coordenadores possuem acesso somente-leitura restrito aos alunos pertencentes ao mesmo `institution_id` (delimitado pelas tabelas de vínculo institucional).
2. **Anonimização em Relatórios Institucionais:** Relatórios agregados de desempenho por turma não expõem detalhes íntimos de horários de dissecção de madrugadas, mas apenas totais consolidados.
3. **Direito ao Esquecimento:** Caso uma conta seja excluída pelo usuário, a regra `ON DELETE CASCADE` vinculada a `auth.users(id)` expurga automaticamente todo o histórico de `user_model_progress` e `user_flashcard_reviews`.

## 5. PLANO E SCRIPT DE ROLLBACK

Caso seja identificada qualquer anomalia operacional durante o rollout futuro no Supabase oficial (Missão P0.17), o plano de rollback foi redigido e validado para execução imediata:

**Arquivo:** `supabase/rollback-plans/rollback_20261118120000_p0_16_academic_metrics_expansion.sql`

```sql
-- ROLLBACK P0.16: REVERSÃO DA EXPANSÃO DE MÉTRICAS ACADÊMICAS
BEGIN;

-- 1. Excluir RPCs canônicas
DROP FUNCTION IF EXISTS public.get_student_academic_summary(UUID);
DROP FUNCTION IF EXISTS public.sync_student_model_progress(UUID, TEXT, INT, INT, INT, BOOLEAN, JSONB);

-- 2. Excluir tabelas criadas pela expansão
DROP TABLE IF EXISTS public.user_flashcard_reviews CASCADE;
DROP TABLE IF EXISTS public.user_model_progress CASCADE;

-- 3. Excluir tipos de telemetria criados
DROP TYPE IF EXISTS public.flashcard_retention_stage CASCADE;

COMMIT;
```

A execução do rollback restaura o banco de dados exatamente ao estado do commit da P0.14.2 sem perda de nenhum dado de autenticação, sessões ou notificações institucionais.
